## Why this batch is not all of slice 2

§117.1 lists slice 2 as identity *and* distribution. Most of the identity half
needs a Supabase project that does not exist yet — a real issuer, JWKS, and the
consent APIs. Building against a provider you cannot reach produces code nobody
has run.

**So this batch is the part that needs no provider and no new dependency.** It
is most of the surface, and all of it is testable today.

**Explicitly out of scope. Do not start any of it:**

- JWT/JWKS verification. It needs a new dependency, and which one is a decision
  for the maintainer, not this session.
- The `/oauth/consent` page's calls to Supabase (`getAuthorizationDetails`,
  `approveAuthorization`, `denyAuthorization`).
- OAuth grant listing and revocation.
- Any live provider smoke test.

If a task below seems to need one of those, you have misread it. Stop and say so.

## A spec decision that this brief resolves

§112 says `/api/v1/*` "rejects a Forma PAT as general REST authentication". Read
literally that contradicts §109.2, which has `forma-mcp` forward the caller's
credential to `forma-server` — every MCP tool call is a REST call.

**Resolution for this batch: `forma-server` validates PATs on `/api/v1/*`.**
There is one verifier, in one place, for both entry points; two verifiers can
disagree about who someone is. §112's table describes what each *product
surface* uses — a browser session is never a PAT — not what the server refuses.
A PAT reaching REST directly is the same account with the same permissions, and
useful for scripting.

Implement it that way. If you disagree, say so in your summary; do not implement
the other reading.

## Task 1 — the SPA can be reached at more than one URL

Measured against the built app today:

```
GET /                -> 200
GET /oauth/consent   -> 404
GET /login           -> 404
GET /agents          -> 404
```

`apps/server/src/main.rs:122` mounts `actix_files::Files` with `index_file` and
no `default_handler`; `index_file` answers a directory request only.
`apps/web/src/App.tsx` says "Two views, no router" — which was right for V1 and
is what §110.3 is the first real reason to change.

**Server.** Add a `default_handler` that serves `index.html` for any path that
is not a file and does not start with `/api/`. A `/api/` path that matches no
route must keep answering 404 in the §32 envelope — never the app shell, which
would turn a typo'd API call into an HTML body a client cannot parse.

**Frontend.** Add routing for `/`, `/login`, `/oauth/consent`, `/agents`.
**Do not add `react-router`.** Three static paths and one query parameter do not
earn a dependency; a small switch on `window.location.pathname` is enough, and
`App.tsx`'s own comment anticipated exactly this moment. Keep `/login` and
`/oauth/consent` as honest placeholders for now — a heading saying what the page
will do — because their content needs the provider. `/agents` is task 3.

**Tests.** Extend `e2e/` so a real browser reaches each path and gets the app
rather than a 404, and add a server test that `/api/v1/nonsense` is still a §32
404.

## Task 2 — Content Security Policy

§110.4 gives the exact policy and it is nearly free: the editor's fonts are
self-hosted woff2, there is no CDN, no Google Fonts link, and no `fetch` to any
absolute URL in `apps/web/src`.

```
default-src    'self';
script-src     'self';
style-src      'self';
style-src-attr 'unsafe-inline';
img-src        'self' data: blob:;
font-src       'self';
connect-src    'self';
frame-ancestors 'none';
base-uri       'none';
object-src     'none';
```

`style-src-attr 'unsafe-inline'` is required — React writes inline `style`
attributes and attribute styles cannot execute script. `img-src data:` is
required because the renderer embeds asset bytes as data URIs. When
`FORMA_SUPABASE_URL` is configured, append that one origin to `connect-src` and
nothing else.

**Set it in `forma-server`, not in Caddy.** A header only present in the hosted
deployment is a header no test ever sees; one served by the binary is exercised
by the Playwright walkthrough on every run.

**Verify it does not break the editor.** Run the e2e suite and look for CSP
violations in the console — a policy that silently breaks the canvas is worse
than none. If something violates it, report what and why rather than loosening
the policy to fit.

## Task 3 — personal access tokens (plan §112.1)

The `api_keys` table already exists from the accounts migration: `id`,
`account_id`, `created_by_user_id`, `name`, `token_prefix`, `token_hash`,
`created_at`, `last_used_at`, `revoked_at`. Nothing writes to it yet.

This is what makes a CLI agent reach one person's account instead of the whole
deployment, and it needs no identity provider at all.

**Format.** `forma_pat_<secret>`, at least 32 random bytes before encoding. Use
`uuid::Uuid::new_v4()` twice — 244 bits from the OS CSPRNG through `getrandom`,
and no new dependency. Store only the prefix and a hash; **use `blake3`**, which
is already in the tree, already used for the deployment token, and whose `Hash`
compares in constant time. Show the complete token exactly once, on creation.

**Repository.** Extend `AccountRepository` (or add `ApiKeyRepository` if that
reads better — your call, say which and why): create, list for account,
authenticate by presented token, touch `last_used_at`, revoke.

**Server.** `POST /api/v1/api-keys`, `GET /api/v1/api-keys`,
`DELETE /api/v1/api-keys/{id}` — all account-scoped through `AuthContext` like
everything else, and all subject to the same rule as every other object: a key
belonging to another account answers 404, never 403.

**Auth.** `require_bearer` accepts a PAT as well as `FORMA_REMOTE_TOKEN`, and a
PAT resolves an `AuthContext` with `kind: McpPat`, `api_key_id`, and the
account the key belongs to. §117.2 already maps that to `actor_id = pat:<id>`;
make sure a mutation authenticated by a PAT records that, and add the test.

**Non-negotiable.**
- A revoked key fails on the very next request. Test it.
- Revoking one key disconnects nothing else — not other keys, not the
  deployment token. Test it.
- Never log a presented token, a stored hash, or a prefix at any level.
- `last_used_at` must not turn every read into a write on the hot path. Say what
  you chose and why.

## Task 4 — the MCP 401 challenge and Protected Resource Metadata (§111.2)

`apps/mcp/src/http.rs` already answers 401 in the §32 envelope. A standards-based
MCP client needs one header more to discover where to authenticate:

```
WWW-Authenticate: Bearer resource_metadata="https://<domain>/.well-known/oauth-protected-resource/mcp"
```

Serve that document from `forma-mcp`:

```
GET /.well-known/oauth-protected-resource/mcp
```

```json
{
  "resource": "https://<domain>/mcp",
  "authorization_servers": ["<FORMA_SUPABASE_ISSUER>"],
  "bearer_methods_supported": ["header"]
}
```

**It is configuration-driven, and absent when unconfigured.** With no
`FORMA_SUPABASE_ISSUER` there is no authorization server to name, so the route
answers 404 and the challenge header omits `resource_metadata` rather than
advertising a resource nobody can authenticate against.

**Caddy.** `deploy/caddy/Caddyfile` routes `/mcp*` with `uri strip_prefix /mcp`.
`/.well-known/oauth-protected-resource/mcp` does not match `/mcp*`, so today it
falls through to `forma-server` and 404s. Add its own `handle` block to
`127.0.0.1:4766` **without** `strip_prefix`, and make sure `forma-mcp` receives
the path it expects. Say in your summary how you confirmed the two agree.

**Do not** touch rmcp's `allowed_hosts`, and never call
`disable_allowed_hosts()` — an empty allowlist means allow everything.

## Ground rules

- `cargo test --workspace`, strict clippy, `cargo fmt --all --check`, and
  `./scripts/check.sh` all clean before anything is done.
- **Never weaken a test to make it pass.**
- No new dependencies, in Rust or in the frontend. If you believe one is
  unavoidable, stop and say which and why instead of adding it.
- **No `any` in TypeScript, ever** — the type-aware lint rules run as errors and
  `pnpm lint` uses `--max-warnings 0`. Untyped data enters the app in exactly one
  place, `readJson` in `apps/web/src/api.ts`. Do not widen that boundary.
- Rust is the source of truth for types: new DTOs are `ts-rs` exports in
  `bindings/generated/`, committed, never hand-written in TypeScript.
- Commit each task separately. If a fix needs a behaviour change, put it in its
  own commit and lead the message with it.
- End messages with `Co-Authored-By: Codex <noreply@openai.com>`.
- Nothing pushed, nothing deployed, the VM untouched.

**For each task, prove the test can fail.** Break the thing on purpose, watch the
right test go red, restore, and say in your summary which one you broke. Two of
the three slice 1 follow-ups were checked that way and it is the only reason I
trust them.
