## The provider, verified rather than assumed

A Supabase project exists and was checked from this machine on 2026-08-31. These
are measured values, not documentation:

```
issuer                 https://wxlxhgxvbfperjkefqdh.supabase.co/auth/v1
jwks_uri               <issuer>/.well-known/jwks.json
authorization_endpoint <issuer>/oauth/authorize
token_endpoint         <issuer>/oauth/token
registration_endpoint  <issuer>/oauth/clients/register     (DCR is on)
scopes_supported       openid profile email phone offline_access
grant_types            authorization_code refresh_token
```

The JWKS publishes **one** key: `alg: ES256`, `kty: EC`, `crv: P-256`,
`use: sig`, `key_ops: ["verify"]`, with a `kid`. There is no `oct` entry.

**Two facts about that which change how the verifier is written:**

- OIDC discovery advertises `id_token_signing_alg_values_supported:
  ["RS256","HS256","ES256"]` — three algorithms, while this project signs with
  one. That list is GoTrue's generic capability, not this deployment's policy.
- `code_challenge_methods_supported` includes `plain` as well as `S256`.

Neither is a defect. Both are the reason the rules in task 1 are absolute.

**Two more, from `GET /auth/v1/settings` on the same project:**

- `email: true`, and every social provider false. Magic link is the only way in,
  which is what §110.2 asks for.
- **`mailer_autoconfirm: false`.** This one is load-bearing rather than
  incidental. The invite gate in task 4 matches an invite against the user's
  email, so the whole gate rests on that address having been *proven*. With
  autoconfirm off, a person only holds a session after following a link sent to
  the address, so the claim is verified. If it were ever turned on, anyone could
  register as an invited address and walk in — so the gate must read the
  provider's verified-email claim and not a self-asserted one. Say in your
  summary which claim you used.
- `disable_signup: false`, so anyone may create a Supabase identity. That is
  fine and expected: §107.3 puts the gate on owning an account, not on signing
  in, and an identity with no membership reaches nothing.

The frontend's two values are in `apps/web/.env` (gitignored) with
`apps/web/.env.example` committed beside it.

## Dependencies

This batch adds exactly two, and no others:

- **Rust: `jsonwebtoken`**, for signature verification only. The JWKS cache is
  ours — see task 1 — because the cache policy is where the substance is and I
  would rather own it with tests than inherit someone's judgement.
- **Frontend: `@supabase/supabase-js`**, for the browser session. Unavoidable;
  it is the client for the auth API.

**On typing supabase-js.** Its documented "TypeScript support" is about
generating a `Database` type from a schema for `.from()` queries. We make no
queries — this project uses Auth only and has no tables — so that generic would
be a generated file describing nothing and a parameter affecting no call we
make. Do not generate it.

What does apply is the invariant it exists to serve. The auth methods
(`getSession`, `signInWithOtp`, `auth.oauth.*`) ship typed with the package;
narrow their unions explicitly and never reach for `any` or a disable comment to
get past one. `readJson` in `apps/web/src/api.ts` stays the only place untyped
data enters the app. If 2C adds the approved-agents table, generating types
becomes worth doing then.

Anything else: stop and say what and why.

You will need `VITE_SUPABASE_PUBLISHABLE_KEY` (an `sb_publishable_…` value) from
the maintainer, out of Project Settings → API Keys. It belongs in the browser by
design: Vite bakes `VITE_*` values into the bundle at build time rather than
reading them at runtime, so it is public to anyone who opens the editor. That
also means it must be present when `pnpm build` runs — on the build machine, not
in the server's environment file — which is a deployment detail to record rather
than discover. **There is no
`service_role`/`sb_secret_…` key in this batch** — validating user JWTs and
using the consent APIs does not need one, and it must never reach the SPA.

## Task 1 — the JWT verifier and the JWKS cache (§111.4)

The security-critical piece of the whole phase. Build it first, in isolation,
with tests that do not touch the network.

**Verification is absolute about all of this. Every item is a rejection, not a
warning:**

```
algorithm      exactly ES256. Never read from the token's own header, never
               from discovery. A token whose header says anything else is
               refused before its signature is considered.
kid            must name a key currently published in the JWKS.
issuer         exact string equality with FORMA_SUPABASE_ISSUER.
exp            required, in the past is a rejection.
nbf            when present, in the future is a rejection.
sub            required, and must parse as a UUID (it becomes AuthUserId).
aud            required. See below.
```

**Do not trust the token to tell you how to verify it.** That is the whole
lesson of the three advertised algorithms: the deployment signs with ES256 and
the verifier accepts ES256, and no message from the network changes that.

**Audience.** Do not assume what Supabase puts there. Obtain a real browser
session token against the configured project, read its claims, and pin what is
actually issued. Write the observed value into the test as a fixture and say in
your summary what you measured. Guessing this is how an audience check becomes
decoration.

**The JWKS cache.**

- Fetched with `reqwest`, which is already in the tree.
- Never fetched on the request path in the common case. A verification with a
  known `kid` must not touch the network.
- An **unknown `kid` may trigger one refresh** — that is how key rotation is
  survived without a restart — but rate-limit it with a floor. Without one, a
  stream of tokens carrying invented `kid`s turns every request into an outbound
  fetch, which is a denial of service someone else pays for.
- A refresh that fails must not empty the cache. Keys that verified a second ago
  still verify.
- Supabase asks for ~20 minutes of propagation after a key change; a refresh
  policy that assumes instant consistency will produce confusing failures.

**Tests, all offline.** Generate an ES256 keypair in the test, serve a JWKS from
a fixture, and mint tokens for each case: valid; expired; not-yet-valid; wrong
issuer; wrong audience; `alg` header set to RS256; `alg` header set to HS256 and
signed with the public key as an HMAC secret; unknown `kid`; missing `sub`;
`sub` that is not a UUID; a signature that does not verify; rotation, where a new
`kid` appears and the old one still works.

The HS256 case is not theoretical padding. It is the classic confusion attack,
and a verifier that reads `alg` from the token accepts it.

## Task 2 — resolving an AuthContext from a browser session (§108, §111.4)

`AuthContext` and `AuthKind::BrowserUser` already exist and are unused.
`apps/server/src/routes/helpers.rs` has `auth(&state)`, which today always
answers `AuthContext::local(state.account)` and whose doc comment says the
hosted slice replaces its body and nothing else. Do that.

```
verified JWT -> sub -> AccountMembership -> AccountId
```

`AccountRepository::membership_of` already exists. No membership means a valid
identity that is not an authorized Forma account: **403 `ACCOUNT_REQUIRED`**,
which is the only 403 in this codebase and already wired
(`ApiError::forbidden`). Never 403 for an object in another account — that stays
a 404, per §108.2 and the tests in `apps/server/tests/tenancy.rs`.

`require_bearer` accepts, in `FORMA_AUTH_MODE=supabase`: a verified Supabase
session JWT, or a PAT. In `local` it keeps exactly the behaviour it has now.

**The actor follows for free.** §117.2's mapping is implemented and tested;
`AuthKind::BrowserUser` already yields `user:<sub>`. Confirm a mutation made
through a hosted browser session records that, and that the `x-forma-actor`
header cannot override it.

**Startup.** `main.rs` currently exits when the mode is `supabase`, saying it is
not built. Remove that, and let `Config::binding_is_safe` do its job — it
already refuses to start without the issuer and JWKS configuration.

## Task 3 — the login page (§110.2)

`/login` is a public placeholder today. Make it real with Supabase email
magic-link / OTP through `@supabase/supabase-js`.

```
no session      -> render login
valid session   -> Authorization: Bearer <access token> on every /api/v1/* call
401 from REST   -> refresh the Supabase session;
                   if none remains, return to login
```

**No second Forma session cookie.** §106.2 is explicit, and an earlier attempt
at one was deliberately reverted. The Supabase session is the session.

`apps/web/src/api.ts` is the single place untyped data enters the app, through
`readJson`. Attach the bearer there, in the one function every call already goes
through — not per call site.

**Local mode must not ask for a login it does not have.** The editor needs to
know whether this deployment has identity at all before it draws anything: a
local Forma has no session and must go straight to the workspace. Add a small
public endpoint that says so and nothing else — no account data, no user, no
provider secrets — and gate the first render on it.

## Task 4 — onboarding: invite, create, or claim (§107.3, §113.1)

A verified identity with no account currently gets a 403 and a dead end. Give it
the two doors the plan names, and no third one.

```
No Forma account yet
[ Create my account ]

Existing deployment?
[ Claim existing workspace ]
```

**Create** requires an unclaimed invite matching the user's verified email.
`AccountRepository::open_invite` and `claim_invite` exist, and
`forma-server invite <email>` mints them. Everything else is refused, worded as
a state rather than a failure: *this Forma is invite-only*. Signing in is not
the gate; owning an account is.

**Claim** is `POST /api/v1/bootstrap/claim`, and it requires **both** a valid
session **and** the deployment's `FORMA_REMOTE_TOKEN`.
`AccountRepository::claim_bootstrap` already enforces once-only with a guarded
UPDATE. On success the token stops being accepted as general authentication —
it becomes a migration secret, not a credential.

Show the claim door **only** while an unclaimed bootstrap account exists.

**Test the hostile cases, not only the happy one:** a second claim; a claim with
a valid session and no token; a claim with the token and no session; a create
with no invite; a create with an invite belonging to a different address; and an
invite whose address differs only in case or surrounding space.

## Ground rules

- `cargo test --workspace`, strict clippy, `cargo fmt --all --check` and
  `./scripts/check.sh` clean before anything is done.
- **Never weaken a test to make it pass.**
- **No `any` in TypeScript, ever.** `pnpm lint` runs `--max-warnings 0` with the
  type-aware rules as errors. `readJson` is the only place untyped data enters.
- Rust is the source of truth for types: new DTOs are `ts-rs` exports in
  `bindings/generated/`, committed, never hand-written in TypeScript.
- Never log a token, an `Authorization` header, a JWT, a PAT or a hash — at any
  level, including `debug`.
- Commit each task separately. A behaviour change gets its own commit and leads
  the message.
- End messages with `Co-Authored-By: Codex <noreply@openai.com>`.
- Nothing pushed, nothing deployed, the VM untouched.

**For each task, prove the test can fail.** Break it on purpose, watch the right
test go red, restore, and say which one you broke. For task 1 specifically:
remove the algorithm pin and confirm the HS256 confusion test fails. If it still
passes, the test is wrong and the verifier is unproven.
