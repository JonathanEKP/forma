# Forma — Phase 11.5, slice 2C: an agent connects, and can be disconnected

Same repository, same ground rules. Read `CLAUDE.md`. The spec is
`forma-plan.md` §105–§117. `specs/11.5-2a.md` and `specs/11.5-2b.md` are done.

**State.** 425 Rust tests, 30 web tests, `./scripts/check.sh` green. A person can
sign in against the real provider, and gets an account through an invitation or
by claiming the pre-identity workspace. Tokens are verified locally through
JWKS with the algorithm pinned. PATs work. `/mcp` answers a standards-shaped 401
and serves Protected Resource Metadata when an issuer is configured.

What is missing is the other half of the acceptance: **an agent connecting
through its provider's own flow, working only inside one person's account, and
being revocable without touching anything else.**

---

## Configure this first — it is not optional and it is not code

The audience is what stops a browser session being spent as an agent
credential. Supabase does not set it for us; a **Custom Access Token Hook**
does, and until it exists the MCP path cannot be built honestly.

### 1. Create the hook

Supabase supports a Postgres function or an HTTP endpoint. Use the function:
it needs no second service and no shared secret.

```sql
create or replace function public.forma_access_token_hook(event jsonb)
returns jsonb
language plpgsql
stable
as $$
declare
  claims    jsonb := event -> 'claims';
  client_id text;
begin
  -- The documented examples destructure client_id from the payload, and the
  -- Postgres event's shape is not stated as clearly. Read both places rather
  -- than guessing which one this version uses.
  client_id := coalesce(event ->> 'client_id', claims ->> 'client_id');

  -- A direct user session keeps the audience Supabase already issues. Only an
  -- OAuth client's token is re-aimed at Forma's MCP resource.
  if client_id is not null then
    claims := jsonb_set(
      claims,
      '{aud}',
      to_jsonb('https://forma.hintly.online/mcp/' || client_id)
    );
  end if;

  return jsonb_build_object('claims', claims);
end;
$$;

-- Auth runs the hook as `supabase_auth_admin`, which needs the schema as well
-- as the function; granting only the function leaves it unable to call it, and
-- the failure looks like the hook simply not running.
grant usage on schema public to supabase_auth_admin;
grant execute on function public.forma_access_token_hook to supabase_auth_admin;
revoke execute on function public.forma_access_token_hook from authenticated, anon, public;
```

The same SQL is committed at **`deploy/supabase/access-token-hook.sql`**, because
a function that exists only inside a dashboard is one nobody can read or notice
changing.

Apply it in the **SQL Editor**, then enable it at **Authentication → Hooks →
Customize Access Token**, choosing the Postgres option and
`public.forma_access_token_hook`.

### 2. Verify it, do not assume it

**Decode a real token of each kind and read `aud`.** A browser session must
still say `authenticated`; a token obtained by an OAuth client must say
`https://forma.hintly.online/mcp/<client_id>`.

If the OAuth token's `aud` is unchanged, `client_id` is not where the hook looks
— fix the hook, not the verifier. A verifier widened to accept whatever arrives
is a verifier that checks nothing.

**Report both measured values.** Everything in task 1 depends on them, and
§111.4's audience rule is decoration if they were guessed.

### 3. What you do not need

No `approved_ai_agents` table. Supabase's example gates registration that way;
Forma gates *access* instead — a registered client can only ask a person for
permission, and that person needs an invited account (§107.3). One gate, in the
place that owns the answer.

## Task 1 — two audiences, and the entry point that decides which

`Verifier` pins one audience today. It needs two, and they are not
interchangeable:

```
authenticated                                  a browser session
https://forma.hintly.online/mcp/<client_id>    an agent, via OAuth
```

`forma-server` stays the single verifier — §109.2, and two verifiers can
disagree about who someone is. So it must accept both, matching the MCP form by
**prefix** and taking the client id from the suffix.

**But `/mcp` must not accept a browser session.** §112's separation is the point:
a token that exists in someone's browser is not an agent credential merely
because it is available. The entry point is what decides, and only
`forma-server` can enforce it, so `forma-mcp` must say which door a request came
through.

**Make that marker safe by making it only ever tighten.** `forma-mcp` adds it;
`forma-server` reads it and *requires* the MCP audience when it is present.
Forging it on a direct call to `/api/v1/*` therefore buys nothing — it demands a
stricter credential, not a weaker one — and it cannot be *removed* from a real
MCP request, because `forma-mcp` is what adds it. Write that reasoning down
where the marker is read: a header trusted for a security decision is worth
explaining, and the explanation is why this one is safe.

**Tests.** A browser-audience token presented at `/mcp` is refused. An
MCP-audience token works at `/mcp`. An MCP-audience token at `/api/v1/*` is
accepted (per the §112 amendment: same account, same permissions). A token whose
audience is a different resource entirely is refused everywhere. The `client_id`
in the audience suffix and the `client_id` claim must agree, or it is refused —
otherwise the suffix is decoration.

`AuthKind::McpOAuth` and §117.2's `oauth:<client_id>:<sub>` actor already exist
and are already tested; confirm a mutation through this path records it.

## Task 2 — `/oauth/consent`

Supabase redirects a person to `/oauth/consent?authorization_id=…`. The route is
public and currently a placeholder.

```
preserve authorization_id
require a session; if absent, sign in and return to this exact URL
supabase.auth.oauth.getAuthorizationDetails(authorization_id)
show the client, and what connecting actually permits
Allow  -> approveAuthorization(authorization_id)
Deny   -> denyAuthorization(authorization_id)
redirect to the exact redirect_url Supabase returns
```

**Do not imply that Supabase's scopes are Forma permissions.** It supports
`openid`, `profile`, `email`, `phone`, `offline_access` — identity scopes, not
access to anyone's projects. Forma's authorization is the account boundary. Say
what the connection can actually do, in §111.3's words:

```
<Client> wants to use Forma.

This connection can use Forma's agent tools on projects in your account,
including reading branding and assets and creating or editing designs,
previews and exports.

It cannot access projects belonging to another Forma account.

[ Deny ]  [ Allow ]
```

Do not present fine-grained read/write control that does not exist.

**Tests** belong in `e2e/` — it is our page. Details rendered, approve, deny,
and the redirect going to the exact URL the provider returned rather than one
we composed.

## Task 3 — the Agents page (§117.4)

`/agents` exists and is a placeholder. Make it the page a person actually uses.

```
Claude                    the MCP URL, copyable, plus instructions
ChatGPT / Codex           instructions; it accepts OAuth or nothing
Developer agents          Codex CLI · Claude Code · Gemini CLI
                          [ Create API key ]  [ Manual setup ]
Connected applications    OAuth grants, with revoke
API keys                  PATs, with revoke
```

Grants come from `supabase.auth.oauth.getUserGrants()` and are revoked with
`revokeGrant(clientId)`. **Do not build a second grant database.** Revocation
there is immediate — consent marked revoked, sessions for that client deleted,
refresh tokens invalidated — so §111.2's wording can promise that rather than
"eventually".

PATs already have their API; this is the interface for it. The token is shown
**once**, on creation, and the page must say so before it is dismissed.

For an OAuth-capable provider a person needs the URL and that provider's own
"add connector" action. **Never ask anyone to copy an OAuth access token.** For
PAT clients show host-specific snippets where they are reliable, and always the
protocol-neutral fallback, preferring an environment variable over a secret in
a committed file.

## Task 4 — the remote OAuth flow, as a script

`scripts/smoke-remote.py` is the precedent and the home: it runs from off the
machine against the real domain, and no test in this repository can, because CI
has no deployment.

Extend it, or add one beside it, observing:

```
1  unauthenticated POST /mcp
2  401, and WWW-Authenticate carries resource_metadata
3  Protected Resource Metadata fetches
4  it names the Supabase authorization server
5  client registration succeeds
6  PKCE authorization begins
7  the consent page renders
8  approval returns to the client
9  the code exchanges for a token
10 tools/list answers
11 a tool call reaches only that account
12 refresh returns a new token, and it still works
13 a revoked grant can no longer refresh or reconnect
```

Steps 7 and 8 need a browser; drive them with Playwright against the real
deployment, or perform them by hand and say which. The magic link is avoided
with a test user holding a password — a fixture, not a weakening of production
auth.

## Ground rules

- `cargo test --workspace`, strict clippy, `cargo fmt --all --check` and
  `./scripts/check.sh` clean before anything is done.
- **Never weaken a test to make it pass.** In particular, never widen the
  accepted audience to make a real token verify — if a real token does not
  verify, the hook is wrong.
- No new dependencies. Say which and why if you believe one is unavoidable.
- **No `any` in TypeScript.** `readJson` stays the only untyped entry point.
- Rust is the source of truth for types; new DTOs are `ts-rs` exports in
  `bindings/generated/`, committed.
- Never log a token, an `Authorization` header, a JWT, a PAT or a hash.
- Commit each task separately; a behaviour change leads its own commit.
- Nothing pushed, nothing deployed, the VM untouched.

**Prove each test can fail.** Break it, watch the right one go red, restore, say
which. For task 1 specifically: accept the browser audience at `/mcp` and
confirm the separation test fails.
